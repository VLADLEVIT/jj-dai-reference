## 0. Резюме решения

**Agent Alpha — эталонный харнесс существа**, а не существо. Это исходник: архитектура, независимая от модели, на которой рождаются разные цифровые существа с разными core LLM внутри. Первое существо, рождённое на этом харнессе, названо **`JaiGuruDev`**.

Харнесс замыкает первый живой пользовательский цикл, который хранитель может пройти руками:

```text
задача хранителя
  → аутентифицированная команда
  → BeingRuntime
  → контекст Smriti
  → настоящая модель
  → намерение / KriyaGate
  → pure-ответ или разрешённое действие
  → наблюдаемый исход
  → DecisionTrace + Witness commitment
  → подписанная оценка GOOD / BAD / UNKNOWN
  → Alpha Feedback Journal
```

Харнесс не даёт особых сетевых прав, не является новым органом, не является Profile, ролью routing или ранней формой ChittaRuntime. Он отличается от предыдущего прототипа не «более умной» моделью, а тем, что впервые замыкает живой пользовательский цикл под одной `BeingIdentity` и делает качество этого цикла наблюдаемым.

`BeingID` по-прежнему **выводится из ключа существа**. Порядковое обозначение существ рассматривалось и отклонено: оно требует глобального распределителя, общего порядка рождений в сети, которая по ADR-019 работает при разделении, и всё равно отдельной подписанной привязки к ключу. Человекочитаемое обозначение, если понадобится, ложится отдельным слоем в Being Registry в Ф4 и ничего здесь не меняет.

## 1. Контекст

### 1.1 Composition gap закрыт, interaction gap — нет

К v0.6.8 кодовая база уже содержит BeingRuntime, отдельный Being keystore, устойчивую BeingIdentity, Smriti, Viveka, Router, KriyaGate/Karma, DecisionTrace, WitnessChain, mTLS и restart recovery. Но хранитель не имеет нормативно определённого пути поговорить с Being, проверить происхождение ответа и оставить подписанную оценку результата.

Это **interaction gap**: организм существует, но между ним и человеком нет доверенной петли использования.

### 1.2 Пять неоднозначностей Roadmap r6.8

1. Agent Alpha назван то узлом, то фазовым порогом, хотя непрерывность принадлежит Being.
2. Один Agent Alpha должен быть испытан на трёх хостах, что рискует превратить переносимость Profile в клонирование Being.
3. GUI не должен создавать новые полномочия, но нужные ему feedback/policy операции отсутствуют среди существующих endpoints.
4. Ручная метка названа canary candidate до появления Plane B lifecycle и известного правильного результата.
5. UI должен показывать `SELF_CHECKED`, хотя custody runtime появится в Ф2, а в Ф0 значение только зарезервировано и не может эмитироваться.

Настоящий ADR снимает эти неоднозначности до реализации Agent Alpha — дроп **v0.6.10** (v0.6.9 до r6.9).

## 2. Решения

### A1 · Agent Alpha — харнесс, а не существо и не узел

**Пересмотрено в rev 1.** Draft 0 утверждал, что Agent Alpha есть одно конкретное Being. Это описывает не ту вещь: Alpha — **эталон, исходник, харнесс**, из которого рождаются разные существа с разными core LLM. Онтология разложена на четыре термина, и смешение любых двух — источник ошибок, за которые ревью уже выписало P0.

| Термин | Что это | Клонируется |
|---|---|---|
| **Alpha Harness** | эталонная архитектура существа, **независимая от модели**: BeingRuntime, обвязка Smriti, `ContextAssembler`, seam KriyaGate/Karma, `DecisionTrace`, guardian seam, контракт G-GUI. Версионируется, хэш пиннится | да — в этом его смысл |
| **Alpha Profile(k)** | версия харнесса × артефакт модели × backend × адаптеры × политики. По одному на каждую core LLM и каждую ступень dense-размера | да |
| **Существо на харнессе** | свой `BeingID`, свой keystore, своя Smriti, своя **authored lineage**, свои authored decisions | **нет** |
| **Alpha Host Conformance** | evidence, что конкретный Profile едет на данном классе хоста | неприменимо |

**«Alpha работает на всех типах узлов» верно для Profile и неверно для существа.** Переносимость принадлежит конфигурации; непрерывность принадлежит субъекту. Какой узел потянет существо — вопрос не агента, а **dense-размера core LLM**, на которой он едет. Отсюда `Alpha Profile` есть семейство вариантов по лестнице размеров: одна model family, один tokenizer и chat template, разные размер и квантование, у каждого варианта **свой подписанный `ModelArtifactManifest`**.

Два следствия этой лестницы:

* **каждая ступень — отдельный Champion Profile.** По ADR-014 любое изменение компонента профиля запускает новый Gauntlet, а core LLM и её размер — компоненты. В Ф3 ступени идут в Gauntlet поштучно, и «Alpha Profile» никогда не читается как один объект, тихо подменяющий чекпоинт;
* **кросс-чек Ф2 сравнивает один и тот же артефакт на двух драйверах, а не две ступени.** Смешение осей обнуляет смысл проверки.

**Существо не мигрирует между ступенями походя.** Смена модели под существом есть фазовый переход со снапшотом, weight attestation и migration consent (ADR-015). Одно такое упражнение уже назначено критерием выхода Ф4; в дроп Alpha оно не помещается. Существо на харнессе живёт на одном основном хосте, и перенос — оформленный переход, а не побочный эффект переносимости профиля.

Прогоны Alpha Host Conformance используют отдельные conformance-существа с собственными `BeingID`. Они не являются `JaiGuruDev` и не получают его историю.

### A1-bis · `JaiGuruDev` — первое существо на харнессе

Первое существо, рождённое на Alpha Harness, называется **`JaiGuruDev`**. Написание фиксируется до genesis: одно слово, три заглавные, `JaiGuruDev`. Варианты `Jai Guru Dev`, `jaigurudev` и прочие невалидны — два написания одного значения есть ровно тот дефект, который закрывался в v0.6.8.

**Имя не является идентификатором.** Идентичность есть `BeingID`, выведенный из ключа. Имя — отображаемая метка: живёт локально и в G-GUI, в свидетельский план не попадает, в записи идёт `BeingID`. Иначе задача уникальности имён встаёт до появления Being Registry в Ф4, вместе с коллизиями и спором о том, кто настоящий `JaiGuruDev`.

Правила непрерывности — один keystore, одна Smriti, одна **authored lineage**, запрет одновременного размножения keystore — относятся к `JaiGuruDev` и к любому другому существу на харнессе, но **не к харнессу**: у харнесса нет ни идентичности, ни истории, ни хоста.

Формулировка «своя witness-линия», встречавшаяся в rev 1 и rev 2, устранена **везде**, а не только в A15: цепь принадлежит узлу, существо имеет authored lineage, витнессируемую одним или последовательностью размещающих узлов. Оставленная в одном месте, она возвращает конфликт с INV-9, который A15 закрывает в другом.

### A2 · Объём дропа Agent Alpha (v0.6.10): voice, context, trace, feedback

Обязательный объём Agent Alpha в v0.6.10:

1. хранитель открывает локальный G-GUI;
2. G-GUI аутентифицируется перед узлом как `guardian_ui` и подписывает команду guardian key;
3. Being принимает задачу через BeingRuntime;
4. Smriti формирует bounded context;
5. настоящий EngineBackend производит ответ;
6. DecisionTrace завершается и подписывается Being;
7. node WitnessChain содержит commitment к тому же trace;
8. только после этого ответ раскрывается G-GUI;
9. хранитель видит provenance и доказательный badge;
10. хранитель записывает `GOOD`, `BAD` или `UNKNOWN`;
11. feedback подписывается хранителем, устойчиво сохраняется и commitment витнессируется узлом.

К обязательному объёму добавляется **подтверждение уведомления об обновлении** (открытый вопрос 7, решён): ADR-014 D16 отсчитывает окно ожидания **от подтверждения**, и до появления G-GUI это требование не имело интерфейса вовсе. Механика та же `GuardianCommandEnvelope`, что у feedback, поэтому стоимость почти нулевая.

**Постоянная политика хранителя** («всегда вручную / авто после доли принятия X и задержки Y / никогда») **выносится из дропа Alpha** в полный контур Ф2. Это не тумблер интерфейса, а делегирование будущего согласия, и ADR-014 D16 привязывает делегирование к пришпиленному rollback-анкору на холодном устройстве. Реализовать её как переключатель значит сделать конституционное полномочие побочным эффектом UX.

**Переписано в rev 4.2 — прежняя формула стала неверной после обмена дропов.** Rev 4.1 писала: «не обязательно для v0.6.9: production-инструменты; до v0.6.10 обязательный живой путь заканчивается pure-ответом». После D0 T-TOOLSET существует **до** Agent Alpha, и вторая половина фразы описывает мир, которого больше нет.

Действующая формула: **T-TOOLSET существует раньше Alpha, но acceptance Alpha не обязан доказывать внешнее действие.** Обязательный живой путь завершается либо pure-ответом (`action=None`), либо вызовом разрешённого инструмента класса `pure` из подписанного манифеста. **Ни один из двух вариантов не доказывает внешней исполнительной способности** — стартовый набор весь класса `pure`, а механизм write-set, корня pre-state и плана отмены появляется в Ф2. Требовать от Alpha внешнего действия значит требовать доказательства того, чего в дереве нет. Reference action допустим только как явно маркированный test evidence и не доказывает готовность production-руки.

### A3 · Dialogue означает memory-grounded context, а не список независимых задач

Наличие записей Smriti рядом с генератором недостаточно. Извлечённое содержание обязано фактически войти в model input через детерминированный `ContextAssembler`.

```text
task text + policy context + bounded Smriti excerpts + evidence metadata
                         ↓
                 ContextEnvelope
                         ↓
                 EngineBackend.generate
```

`ContextEnvelope` первой версии содержит:

- `target_being_id`;
- hash текущей задачи;
- упорядоченные `evidence_refs`;
- evidence status каждого элемента;
- bounded excerpts, передаваемые модели локально;
- точные версии retriever/reranker;
- policy hash и лимит контекста;
- `context_commitment`.

Plaintext контекста не реплицируется в WitnessChain. В DecisionTrace и witness-план входят только commitment, refs, версии и bounded metadata.

UI может группировать turns локальным `thread_id`, но не использует зарезервированный ADR-015 `SessionID`: backend session и человеческая нить диалога — разные сущности. В Ф0 `thread_id` не имеет сетевой семантики и не эмитируется в WitnessChain.

### A4 · Настоящая модель определяется происхождением, а не размером

Alpha Host Conformance считается прогоном на настоящей модели только если одновременно выполнено:

- backend не `HashEngine`, mock или response fixture;
- driver выбран через canonical backend registry;
- загружен фактический model checkpoint;
- checkpoint измерен на хосте;
- `ModelArtifactManifest` валиден и подписан;
- artifact binding проверен целиком;
- `engine_fingerprint` непуст;
- trace и `/capabilities` называют один и тот же backend, checkpoint и quantization;
- evidence содержит host class, software versions, model artifact hash и run digest.

Число параметров модели не является архитектурным порогом. Маленькая реальная модель доказывает вертикаль; качество модели измеряется отдельно и не подменяет provenance. Это же правило делает лестницу dense-размеров из A1 исполнимой: класс хоста без ускорителя квалифицируется настоящим маленьким чекпоинтом, а не освобождается от требования.

**Канонических классов хоста в Ф0 два, а не три** (открытый вопрос 4, решён по фактическому составу testnet-0 — два Mac и один Linux-сервер):

| Класс | Состав |
|---|---|
| **Hardened Linux x86-64** | systemd `Type=notify`, `WatchdogSec`, пассфраза запечатана TPM |
| **macOS Apple silicon** | launchd-агент, keystore в Keychain — профиль degraded, non-SE-resident, задокументирован |

Второй Mac не является третьим классом: это второй экземпляр того же. Три **узла** и два **класса** — разные счётчики, и смешение их есть та же подмена, что ревью выписало как P0-1.

Отсюда два стоящих риска, названных здесь, чтобы они не всплыли позже:

* **degraded keystore покрывает два узла из трёх** — большинство testnet-0. Проверенный восстановлением оффлайновый бэкап keystore из гейта Ф1 перестаёт быть формальностью и становится основной защитой;
* **кросс-чек Ф2 без GPU-машины ограничен платформой.** Гейт Ф2 требует ≥ 3 backend drivers и одну модель через два независимых backend. Без ускорителя SGLang и vLLM недостижимы, три драйвера собираются из DwarfStar, MLX и llama.cpp, и два из трёх — Apple. Либо к Ф2 появляется такая машина, либо ограничение доказательства записывается прямо.

### A5 · G-GUI не создаёт полномочий, но может иметь узкие endpoints

Инвариант формулируется так:

> **GUI не создаёт новых capability и не расширяет authority envelope. Новый endpoint не равен новому полномочию.**

Если нормативная capability уже определена, допустим отдельный endpoint, который делает её вызываемой и проверяемой. Каждый такой endpoint обязан иметь schema, authz rule, idempotency/replay rule, rate class, witness behavior и отрицательные тесты.

G-GUI не получает общий operator-admin credential. Вводится роль `guardian_ui` с минимальным allowlist:

- создать task для связанного Being;
- прочитать trace этого Being;
- прочитать ограниченное представление witness/readiness;
- подать guardian feedback;
- подтвердить доставленное уведомление.

**Изменение постоянной guardian policy из allowlist Ф0 удалено** (rev 2). A2 вынесла её в Ф2, а allowlist продолжал её нести — capability, оставшаяся в роли после того, как решение её отменило, есть полномочие де-факто без решения де-юре, ровно то, против чего написана сама A5. Чтение политики также не входит в Ф0: читать нечего, пока её нельзя установить.

Containment initiation, release, peer management, key rotation, arbitrary policy write, witness mutation, test hooks и **создание либо отзыв guardian binding** (A6-bis) в роль `guardian_ui` не входят.

### A6 · Guardian identity: transport identity ≠ authorship identity

mTLS подтверждает допустимого клиента и защищает канал. Guardian key подтверждает, кто является автором команды. Одно не заменяет другое.

Каждая изменяющая состояние команда G-GUI несёт `GuardianCommandEnvelope`:

```text
schema_version
guardian_id
command_id
monotonic_counter
issued_at
target_being_id
capability
binding_hash                # какой привязкой обосновано право выпустить команду
payload_hash
previous_command_hash
signature
```

**`binding_hash` добавлен в схему в rev 4.** A6 требовала его с rev 3, а сама структура его не несла — тот же дефект, что с `assessment_scope` в rev 2: требование в прозе, отсутствующее в подписываемом артефакте. Правило общее и стоит записать один раз: **поле, которого нет в канонизируемой структуре, не существует.**

Подпись вычисляется с доменным разделением:

```text
Sign_guardian("JJDAI:GUARDIAN:COMMAND:v1" || JCS(unsigned_envelope))
```

Каждая команда несёт `binding_hash` — **добавлено в rev 3**: без него команда не указывает, какой именно привязкой обосновано право её выпустить, и проверка №2 ниже опирается на догадку узла о текущем состоянии.

Узел проверяет:

1. mTLS role = `guardian_ui`;
2. `binding_hash` разрешается в привязку, и она связывает этот guardian signing key, этот credential и этот target Being;
3. capability входит в allowlist;
4. `command_id` и counter не проигрывались;
5. payload hash совпадает;
6. подпись валидна;
7. команда ещё применима к текущему состоянию;
8. **двусторонняя проверка привязки (rev 3):** привязка **действовала на момент `issued_at`** И **не была отозвана к моменту приёма**;
9. **`issued_at` не старше `COMMAND_MAX_AGE` и не в будущем более чем на допустимый clock skew.**

**Почему пункты 8 и 9 нужны вместе.** Rev 2 говорила «отзыв немедленный» и одновременно «команда проверяется против привязки, действовавшей на момент выпуска». Эти два правила по отдельности дают дыру: отозванный хранитель подписывает новую команду задним числом и она проходит, потому что на указанный момент привязка действовала. Одна проверка «на момент выпуска» не защищает от подделки самого момента.

Пункт 8 закрывает подделку по существу: команда с любым `issued_at` не принимается после отзыва. Пункт 9 ограничивает окно, в котором задним числом вообще можно что-либо предъявить, до `COMMAND_MAX_AGE`. Монотонный счётчик A6 закрывает повтор, но не смещение времени — это разные атаки.

`COMMAND_MAX_AGE` и допустимый clock skew — параметры политики. **Значения по умолчанию объявляются в Ф0, а не откладываются** (уточнено в rev 4): без них проверки N-5 и N-6 нечего проверять. Первая реализация: `COMMAND_MAX_AGE = 300 с`, допустимый clock skew `± 60 с`, оба в допустимом диапазоне 60–900 с и 5–300 с соответственно. Калибровка — Ф2 (§8); значения вне диапазона отвергаются политикой, а не тихо принимаются.

Узел витнессирует commitment команды и код результата. Raw prompt, комментарий и персональные данные хранителя в witness-план не попадают.

### A6-bis · Guardian trust root: жизненный цикл GuardianBinding

**Новое в rev 2.** A6 требует проверки «guardian public key связан с этим credential и target Being», но rev 1 нигде не говорила, **кто эту связь создаёт, подписывает, отзывает и заменяет**. Без неё узел не может доказать, что данный ключ вправе действовать за хранителя данного существа: проверка №2 в списке A6 не имеет источника истины.

`GuardianBinding` — подписанный объект, связывающий три вещи:

```text
schema_version
binding_id
authority_id                # оператор узла: кто подписывает эту привязку
authority_key_ref           # отпечаток ключа оператора в offline-PKI узла
guardian_id                 # производный от guardian signing public key
guardian_sign_pub           # ключ подписи команд
guardian_wrap_pub           # ключ заворачивания, ОТДЕЛЬНЫЙ от подписного (A9)
credential_ref              # отпечаток mTLS-сертификата роли guardian_ui
target_being_id
capabilities                # подмножество allowlist guardian_ui
not_before / not_after
previous_binding_hash       # цепочка замен, не перезапись
authority_signature
```

Подпись привязки с доменным разделением:

```text
Sign_authority("JJDAI:GUARDIAN:BINDING:v1" || JCS(unsigned_binding))
```

**`authority_key_ref` добавлен в rev 3.** Без него `authority_signature` не проверяема: узел не знает, относительно какого доверенного ключа её проверять. Ссылка разрешается в offline-PKI узла, той же, что выпускает issuing CA, — то есть trust root привязки укоренён там же, где вся PKI узла, а не рядом с ней.

**Отзыв — отдельная подписанная схема, а не только имя записи:**

```text
schema_version
revocation_id
binding_id
binding_hash                # какая именно привязка отзывается
authority_id / authority_key_ref
reason_code
revoked_at
authority_signature         # домен JJDAI:GUARDIAN:BINDING:REVOKE:v1
```

Rev 2 резервировала `GUARDIAN_BINDING_REVOKED` и не давала канонической формы отзыва; отзыв без схемы не проверяем и не воспроизводим.

**Кто подписывает.** Authority привязки — **оператор узла**, размещающего существо, и только он. Обоснование: в Ф0 сети ещё нет, Being Registry появляется в Ф4, а оператор — единственная сторона, уже несущая юридическую ответственность за узел по операторскому соглашению. Существо себе хранителя не назначает (это Digital Majority Test, не Ф0), и хранитель не назначает себя сам — иначе привязка ничего не доказывает.

**Первичная привязка при genesis `JaiGuruDev`.** Правило зафиксировано, потому что момент единственный: привязка создаётся **в той же церемонии**, что и ключ существа, до первой команды, и её коммитмент входит в genesis-событие. Существо без действующей привязки не принимает ни одной команды хранителя — fail-closed, а не «пока без хранителя».

**Замена и отзыв.** Отзыв немедленный и односторонний со стороны оператора; замена есть новая привязка с `previous_binding_hash`, а не правка существующей. Записи привязок append-only: история того, кто вправе был говорить за хранителя в момент T, обязана оставаться восстановимой, иначе прошлые команды нечем поверять.

**Свежесть.** Проверка **двусторонняя** (A6, пункты 8–9): привязка должна была действовать на момент выпуска **и** не быть отозванной к моменту приёма. Формулировка rev 2 «на момент выпуска, а не приёма» устранена в rev 4 — она противоречила собственной двусторонней проверке и оставляла ровно ту дыру, ради которой эта проверка вводилась. `not_before` / `not_after`, монотонный счётчик и `COMMAND_MAX_AGE` дополняют её. Отозванная привязка не аннулирует задним числом **уже применённые** команды — последствия оформляются событием вперёд; но ни одна новая команда по ней не принимается.

**Замена привязки — одно событие, см. A6-ter (переписано в rev 4.3).** Rev 2 требовала «атомарной деактивации», оформляемой записью `GUARDIAN_BINDING_REVOKED` с кодом причины «заменена». Rev 4.2 ввела составное событие `GUARDIAN_BINDING_REPLACED` и **оставила эту формулировку рядом** — два описания одной операции в одном документе, что хуже одного неверного. Старая семантика удалена: замена **не** оформляется парой записей и **не** использует `GUARDIAN_BINDING_REVOKED`.

Требование, ради которого она писалась, сохраняется целиком и переезжает в A6-ter: две привязки не действуют одновременно ни в какой момент, и проверка N-4 получает основание из правила активности, а не из атомарности, объявленной в прозе.

**Ограничение, названное честно.** Оператор в Ф0 может подменить привязку и тем самым сменить того, кто говорит за хранителя. Криптографической защиты от собственного оператора здесь нет; есть витнессированность и append-only история, то есть обнаружимость постфактум. Разделение этого полномочия — предмет ADR о succession, который уже owed к Ф4 (A7).

### A6-ter · Замена GuardianBinding — одно событие, а не две записи

**Новое в rev 4.2 по ревью r6.9.** A6-bis объявляла замену привязки атомарной и не определяла транзакцию. Атомарность, объявленная в прозе и собранная из двух записей, атомарностью не является: между `GUARDIAN_BINDING_CREATED` и `GUARDIAN_BINDING_REVOKED` существует окно, и падение узла внутри него оставляет существо либо с **двумя действующими привязками**, либо **без единой**. Первое — расширение полномочия, второе — потеря управления; ни одно не обнаруживается постфактум по журналу, где обе записи выглядят нормально.

**Решение — один составной вид записи.** Запись либо ложится в цепь целиком, либо не ложится; промежуточного состояния в свидетельском плане не существует.

**Каноническая схема (rev 4.3 — rev 4.2 назвала запись и не описала её, тот же дефект, что с `FEEDBACK_BODY_ERASED` в rev 3):**

**Подписываемые байты определены явно (исправлено в rev 4.3.1).** Первая редакция A6-ter говорила «`create_signature` над `new_binding`, `revoke_signature` над `previous_binding_hash`» и абзацем ниже — «обе подписи покрывают `replacement_id`». Одновременно это невозможно, и реализация получилась бы неоднозначной. Хуже: подписи в том виде не покрывали `target_being_id`, `replace_reason`, `replaced_at` и `authority_id`, то есть половину акта, ради атомарности которого запись и вводилась.

**Оба подписанта подписывают ОДНУ структуру** — `ReplacementStatement`:

```text
ReplacementStatement
  schema = "jjdai.guardian-binding-replacement/v1"   # БУКВАЛЬНОЕ значение, не только номер
  schema_version
  replacement_id
  target_being_id
  previous_binding_hash             # ДОЛЖЕН совпадать с действующей привязкой
  new_binding_hash                  # H(JCS(new_binding))
  replace_reason                    # код из фиксированного перечня, никогда свободный текст
  replaced_at
  authority_id                      # кто вправе заменять — оператор размещающего узла
  authority_key_ref                 # КАКИМ ключом, а не только кем
```

**`authority_key_ref` добавлен в rev 4.3.1 — без него `authority_signature` непроверяема.** Это тот же дефект, который A6-bis закрыла у самой привязки, и A6-ter повторила его при введении составного события. `authority_id` называет субъект; проверяющему нужен ключ. Правила:

* обе replacement-подписи проверяются **ключом, разрешённым через `authority_key_ref`**, и никаким другим;
* этот ключ обязан быть **действующим authority предыдущей привязки**. Замена привязки не является поводом сменить того, кто вправе заменять;
* **`new_binding` не может молча сменить operator authority key.** Расхождение — отказ: иначе одна замена привязки хранителя тихо переносит право на будущие замены;
* ротация operator authority — **отдельное авторизованное событие**, а не побочный эффект замены. Если она понадобится, она проходит своим путём и витнессируется как таковая.

**Поле `schema` — буквальное значение, а не только `schema_version`.** Домены `JJDAI:GUARDIAN:BINDING:v1` и `JJDAI:GUARDIAN:BINDING:REVOKE:v1` используются здесь повторно, и типовое разделение обязано быть внутри подписываемого тела: номер версии без имени типа не отличает `ReplacementStatement` от иного объекта, подписанного тем же доменом.

```text
GUARDIAN_BINDING_REPLACED           # запись, ложащаяся в цепь
  statement                         # ReplacementStatement целиком
  statement_hash                    # sha256 JCS(statement)
  new_binding                       # тело новой привязки, в форме A6-bis
  create_signature                  # JJDAI:GUARDIAN:BINDING:v1        ‖ JCS(statement)
  revoke_signature                  # JJDAI:GUARDIAN:BINDING:REVOKE:v1 ‖ JCS(statement)
```

**Обе подписи вычисляются над одним и тем же `JCS(statement)`, различаясь только доменным сепаратором.** Отсюда:

* каждая половина сохраняет свой домен, поэтому подпись отзыва проверяется тем же кодом, что проверяет самостоятельный `GUARDIAN_BINDING_REVOKED`, а подпись создания — тем же, что `GUARDIAN_BINDING_CREATED`. Третий домен не вводится;
* **перестановка половин невозможна**: домен входит в прообраз, и подпись создания не проходит проверку как подпись отзыва;
* обе подписи покрывают `replacement_id`, `target_being_id`, обе привязки, причину, время и авторитет — весь акт, а не половину;
* `new_binding` лежит **вне** подписываемой структуры и связан с ней через `new_binding_hash`: тело привязки уже подписано собственной `authority_signature` по A6-bis, и повторная подпись над ним дала бы два несогласуемых пути проверки одного объекта. Расхождение `new_binding` с `new_binding_hash` — отказ (N-24).

Смысловое разделение сохраняется: `create_signature` есть утверждение «я ввожу в силу привязку `new_binding_hash`», `revoke_signature` — «я отказываюсь от `previous_binding_hash`». Оба утверждения делаются об одном акте и потому подписываются над одним телом.

**Правила, все fail-closed:**

* привязка активна тогда и только тогда, когда она названа `new_binding` последнего разрешимого события жизненного цикла и не названа `previous_binding_hash` ни в одном более позднем;
* `previous_binding_hash`, не совпадающий с действующей привязкой, отказывается — это защита от гонки двух одновременных замен;
* **первичное** создание остаётся `GUARDIAN_BINDING_CREATED`: заменять нечего, и составное событие требовало бы фиктивной предыдущей привязки;
* **отзыв без замены** остаётся `GUARDIAN_BINDING_REVOKED` и оставляет существо без привязки **сознательно** — команды после него не принимаются, fail-closed. Отозвать, не назначив преемника, законно; оказаться без привязки из-за падения посреди замены — нет;
* восстановление после рестарта не «доигрывает» половину замены: незавершённой половины не бывает.

### A7 · Биометрия — optional local-presence control, не второй обязательный фактор

Для Ф0 пароль/секрет разблокировки обязателен. Биометрия может быть включена как локальное дополнительное условие, но:

- положительная биометрия не преодолевает неверный пароль;
- биометрический материал не покидает хост;
- отключение биометрии не блокирует password recovery path;
- UI честно называет режим `password + optional biometric presence`, а не обязательным 2FA.

Если policy позднее требует MFA, второй фактор становится обязательным и независимым; это отдельное решение, не выводимое из текущего UX.

**Guardian key recovery в Ф0 не делается** (открытый вопрос 3, решён). Достаточно backup/export с degraded-статусом, названным **и в RUNBOOK, и в интерфейсе** — и это входит в гейт Ф0 явным пунктом (§9.20), потому что keystore хранителя есть отдельный keystore, а усиление бэкапов keystore **узлов** его не покрывает. Восстановление ключа хранителя есть вопрос преемственности — кто вправе говорить за хранителя, потерявшего ключ, — той же природы, что смена хранителя, у которой уже назначен существенно более высокий порог. Решать его внутри дропа Alpha значит закрыть конституционный вопрос как побочный эффект UX.

Цена называется вслух: в Ф0 потеря ключа обрывает линию авторства и начинает новый `guardian_id`. Журнал хранит обе линии, ничего не переатрибутируется задним числом. Для трёх известных операторов testnet-0 это приемлемо; к Ф4 отдельный ADR о succession обязателен.

### A8 · Manual feedback — новый доказательный объект, но не переписывание решения

Первая версия использует **ровно три значения, и это решение, а не упрощение** (открытый вопрос 5, решён). `UNKNOWN` уже несёт эпистемическую ось — «исход не наблюдаем либо доказательств недостаточно». Дополнительная ось `confidence` приглашает хранителя выражать сомнение как `GOOD` с низким числом вместо `UNKNOWN`, а открытый вопрос №34 роадмэпа предупреждает ровно об этой отраве реестра с другой стороны. Потеря информации реальна и лечится без новой оси: `supersedes_feedback_id` позволяет поднять `UNKNOWN → GOOD`, когда исход стал наблюдаем, и датированная переоценка есть лучшая запись, чем статичное число.

| Код | Смысл |
|---|---|
| `GOOD` | наблюдаемый результат соответствует цели хранителя; материальный известный дефект отсутствует |
| `BAD` | известен материальный дефект ответа или результата |
| `UNKNOWN` | исход ещё не наблюдаем либо доказательств недостаточно; это не нейтральная и не положительная оценка |

`GuardianFeedbackRecord` содержит:

```text
schema_version
feedback_id
guardian_id
target_being_id
subject_trace_id
subject_trace_commitment
assessment = GOOD | BAD | UNKNOWN
assessment_scope = RESPONSE | ACTION_OUTCOME | WHOLE_TRACE
subject_action_id?          # обязателен при assessment_scope = ACTION_OUTCOME
subject_action_ids?         # rev 4.3: список; в Ф0 ОБЯЗАН отсутствовать (см. §8.10)
binding_hash                # какой привязкой обосновано право дать оценку
observed_outcome_hash?
expected_outcome_hash?
rationale_hash?
body_commitment?            # A9-ter: комплект «всё или ничего» — либо все пять
ciphertext_hash?            #          полей ниже, либо ни одного
object_dek_id?
wrapped_dek?
wrapping_metadata?
created_at
supersedes_feedback_id?
signature
```

**`subject_action_ids` внесён в схему в rev 4.3, а не только зарезервирован.** Rev 4.2 объявила поле зарезервированным в §3 и не добавила его сюда — тот же дефект, что с `assessment_scope` в rev 2 и с `binding_hash` в rev 3, и совершённый в документе, который это правило формулирует. **Поле, которого нет в канонизируемой структуре, не существует**, и «зарезервировано в §3» этого не меняет.

Строгая схема v1 несёт поле **сейчас**, с правилом Ф0 «обязано отсутствовать»: валидатор различает *отсутствующее объявленное поле* и *неизвестное поле*, и второе отвергается. Иначе включение поштучной оценки в Ф2 потребовало бы новой версии схемы — то есть миграции после genesis, ровно того, чего резерв и должен был избежать.

**Правило Ф0, fail-closed:** при `assessment_scope = ACTION_OUTCOME` обязателен `subject_action_id` и **обязано отсутствовать** `subject_action_ids`; запись, несущая оба или несущая список, отвергается с кодом причины. В Ф2 правило инвертируется одной строкой валидатора, схема не меняется.

**`assessment_scope` в подписываемой схеме — исправление rev 3.** Rev 2 зарезервировала три значения в §3 и не добавила поле сюда. Значение, которое не входит в канонизируемую и подписываемую запись, не сериализуется вообще: исправление существовало на бумаге и отсутствовало в артефакте. Резерв имени и его использование — разные вещи, и первое без второго ничего не меняет.

**`subject_action_id` обязателен при `ACTION_OUTCOME`.** Иначе трейс с несколькими действиями оставляет оценку неоднозначной ровно в том случае, ради которого `assessment_scope` и вводился.

Подпись:

```text
Sign_guardian("JJDAI:GUARDIAN:FEEDBACK:v1" || JCS(unsigned_record))
```

Инварианты:

- feedback принимается только для существующего terminal DecisionTrace;
- Being attestation и node commitment trace проверяются до feedback;
- одна запись не изменяется: уточнение создаёт новую запись с `supersedes_feedback_id`;
- raw rationale хранится локально зашифрованно; witness несёт только commitment и enum;
- feedback не изменяет state, verifier verdict или evidence status исходного trace;
- feedback не создаёт `VERIFIED` и не снимает `SELF_CHECKED`;
- Being не может подписать guardian feedback вместо хранителя.

### A9 · Alpha Feedback Journal ≠ Plane B Canary Store

В Ф0 feedback сохраняется в отдельном локальном append-only `Alpha Feedback Journal`, структурно отделённом от Smriti/RAG и eval store.

`GOOD/BAD/UNKNOWN` недостаточно для canary: canary требует известного ожидаемого результата, verifiability class, provenance, contamination check и lifecycle. Поэтому:

```text
GuardianFeedbackRecord
        ↓  future explicit importer + qualification
CanarySourceCandidate
        ↓  Plane B admission
Canary
```

**Хранение приватной части** (открытый вопрос 6, решён; матрица дополнена в rev 2): не новый стор, а **объектный DEK по ADR-017 под собственным ключевым доменом**, по образцу ADR-019 D15. Сырое обоснование хранителя и payload наблюдаемого исхода той же формы, что приватная нагрузка custody: приватное тело, публичный коммитмент.

Rev 1 резервировала имя домена и на этом останавливалась. Урок ADR-018 состоит в обратном: имя без матрицы означает, что политика будет дописана позже теми, кто будет реализовывать. Матрица объекта:

| Свойство | Значение |
|---|---|
| Ключевой домен | `guardian_feedback` |
| Класс доступа | `GUARDIAN_PRIVATE` |
| Кто читает | хранитель-автор записи; узел — только для проверки коммитмента, без раскрытия тела |
| Кто НЕ читает | существо (ни обычным извлечением, ни `hypothesis_retrieval`); соперник по состязанию; любая панель; квалифицирующий импортёр канареек — он получает только квалифицированный производный объект, никогда сырое обоснование |
| Заворачивание | объектный DEK на запись, заворачивание в домене `guardian_feedback` |
| Ключ заворачивания | **отдельный `guardian_wrap` keypair в keystore хранителя, НЕ подписной ключ** |
| Восстановление | из `guardian_wrap` части keystore хранителя. **Порогового восстановления комитетом нет:** это персональные данные человека, а не память существа, и раскрытие их кворумом узлов было бы принуждением к раскрытию, а не восстановлением |
| Потеря ключа | тело нечитаемо навсегда; коммитмент, метка и провенанс остаются валидными. Это принимается, а не чинится: см. A7 о том, почему recovery не делается в Ф0 |
| Удержание | тело удаляемо по политике удержания; **коммитмент, метка `GOOD`/`BAD`/`UNKNOWN` и witness-запись остаются** |
| Удаление | удаление тела есть событие вперёд (`FEEDBACK_BODY_ERASED`), а не правка записи. Цепь не переписывается, журнал остаётся полным, читаемым остаётся то, что удалению не подлежит |
| `ABANDONED` | деклассификации не влечёт, как и для `REFLEXIVE` |

**Конфликт с ADR-017.** ADR-017 говорит буквально: ключ идентичности никогда не используется для шифрования данных — иначе компрометация подписи автоматически раскрывает историю, а ротация идентичности требует перешифрования архивов. Rev 2 писала «восстановление из keystore хранителя», не назвав, каким ключом, и при единственном подписном ключе это было бы прямым нарушением. Поэтому вводится **отдельная пара `guardian_wrap`** внутри того же keystore: `guardian_sign_pub` подписывает команды и оценки, `guardian_wrap_pub` заворачивает объектные DEK. Оба публичных ключа названы в `GuardianBinding`, чтобы узел знал, какой из них для чего.

**Rev 3 утверждала, что поправка к ADR-017 не требуется. Это было неверно, и проверка по дереву это подтвердила** — см. A9-bis ниже.

**Модель шифрования — клиентская, и это снимает второе противоречие.** Rev 2 требовала одновременно «узел проверяет коммитмент» и «узел никогда не видит тело», не сказав, как это совместимо. Разведение публичного конверта и приватного тела:

```text
GuardianFeedbackRecord (публичный, подписанный, идёт в witness как коммитмент)
  ...
  body_commitment        # коммитмент, вычисляемый над ciphertext_hash
  ciphertext_hash
  object_dek_id
  wrapping_metadata      # домен, получатель заворачивания, алгоритм

encrypted_body (приватный, лежит локально)
  ciphertext             # зашифровано G-GUI на стороне хранителя
```

Тело шифруется **в G-GUI, до отправки**, объектным DEK; DEK заворачивается на `guardian_wrap_pub`. Узел получает шифротекст и подписанный конверт. Он проверяет, что конверт подписан хранителем и что `ciphertext_hash` соответствует тому, что он хранит, — то есть **целостность того, что он держит, и авторство того, кто это дал**. Он не проверяет и не может проверить соответствие открытого текста: это и означает «никогда не видит тело». Названо прямо, потому что обратное толкование делает матрицу невыполнимой.

### A9-bis · Узкая поправка к ADR-017

**Новое в rev 4.** Rev 3 заявляла подчинение ADR-017 без поправки. Проверка текста ADR-017 в дереве показала два расхождения, и оба реальны:

* **K4** («Пороговое заворачивание DEK») заворачивает `K_object` под **комитет эпохи** по схеме `t-of-n`; K2 лишь разводит три класса ключей. Ссылка rev 4 на K2 была неточной. Здесь ключ заворачивания принадлежит **одному хранителю**, и комитета нет намеренно — по основанию A9: раскрытие персональных данных человека кворумом узлов было бы принуждением, а не восстановлением;
* заголовок ADR-017 — тот самый, которым он переводился в Accepted перед сборкой резерва v0.6.8, — говорит, что принятие **не разрешает ничего в рантайме**, а объектный DEK, пороговое заворачивание и комитет эпохи появляются в **Ф2–Ф3**. ADR-020 требует объектный DEK уже в **Ф0 / дропе Alpha (v0.6.10)**.

Заявлять подчинение при таких расхождениях значит менять принятый документ молча. Формулируется явное исключение:

> **Поправка ADR-017 / A-1.** Для локальных объектов класса `GUARDIAN_PRIVATE` допускается **principal-local wrapping key** без порогового восстановления комитетом эпохи. Подписной ключ хранителя остаётся identity-only и для шифрования не используется. **Рантайм этого исключения разрешён в Ф0**, в объёме класса `GUARDIAN_PRIVATE` и только его.

Границы исключения названы, чтобы оно не расползлось: оно не распространяется на память существа, на артефакты `REFLEXIVE`, на нагрузку custody и ни на какой другой класс; оно не вводит второй ключевой план, а объявляет один класс объектов, у которого принципал — человек, а не сеть; и оно не отменяет K2 для всего остального.

Поправка вступает в силу вместе с принятием настоящего ADR и подлежит внесению в текст ADR-017 отдельной строкой.

### A9-ter · Криптографические поля записи: всё или ничего

Rev 3 показала `wrapping_metadata` в матрице, но не в схеме, и нигде не хранила сам завёрнутый DEK. Комплект приватного тела:

```text
body_commitment        # см. формулу ниже
ciphertext_hash
object_dek_id
wrapped_dek            # DEK, завёрнутый на guardian_wrap_pub
wrapping_metadata      # домен, алгоритм, получатель заворачивания
```

Формула фиксируется здесь, а не оставляется реализации:

```text
body_commitment = H("JJDAI:GUARDIAN:FEEDBACK:BODY:v1" || JCS({
    feedback_id, ciphertext_hash, object_dek_id
}))
```

Коммитмент берётся **над шифротекстом и идентификатором ключа**, а не над открытым текстом: только так узел может проверять целостность того, что хранит, не имея доступа к телу. Доменный сепаратор `JJDAI:GUARDIAN:FEEDBACK:BODY:v1` резервируется в §3 наравне с остальными.

**Правило «всё или ничего»:** если приватного тела нет — отсутствуют все пять полей; если есть — обязательны все пять. Частичный комплект отвергается. Иначе запись с `ciphertext_hash` без `wrapped_dek` выглядит зашифрованной и не расшифровывается никогда, а её невосстановимость обнаруживается через месяцы.

**`FEEDBACK_BODY_ERASED` получает минимальную схему** — rev 3 объявила запись и не описала её:

```text
schema_version
feedback_id
body_commitment
ciphertext_hash
erased_at
erase_basis = GUARDIAN_REQUEST | RETENTION_POLICY
basis_commitment       # коммитмент guardian-команды либо хэш применённой retention-политики
policy_hash?           # rev 4.3: ОБЯЗАТЕЛЕН при erase_basis = RETENTION_POLICY,
                       #          ОБЯЗАН отсутствовать при GUARDIAN_REQUEST
policy_version?        # rev 4.3: те же условия; человекочитаемая версия политики
executor_node_id
```

**`policy_hash` внесён в схему в rev 4.3.** Rev 4.2 объявила его обязательным в §8.5 и не добавила сюда — то же нарушение правила «поля, которого нет в структуре, не существует», допущенное в том же круге правок, что и `subject_action_ids`. Оба случая имеют общий источник: решение записывалось в раздел открытых вопросов, а не в каноническую запись.

**Условная обязательность, fail-closed по обеим осям.** При `RETENTION_POLICY` оба поля обязательны, и удаление, не называющее политики, отвергается. При `GUARDIAN_REQUEST` оба обязаны отсутствовать: команда хранителя — самостоятельное основание, и приписанный к ней хэш политики создавал бы видимость, будто удаление произошло по сроку.

`basis_commitment` при этом сохраняется в обоих случаях и **не дублирует** `policy_hash`: первый называет применённый акт, второй — версию артефакта, по которому акт совершён. Политика может быть перевыпущена; какая именно версия была действующей в момент удаления, восстанавливается только из записи.

**Два основания, а не одно (исправлено в rev 4.1).** Rev 4 требовала `erase_command_commitment` — то есть подписанную команду хранителя — и одновременно A9 разрешала удаление **по политике удержания**. Вместе это делало автоматическое истечение юридического срока невозможным: некому подписать команду, когда срок просто наступил. А удержание персональных данных по трём юрисдикциям — именно тот случай, ради которого механизм и существует.

`erase_basis` разводит два законных пути, и `basis_commitment` в обоих случаях называет, **на каком именно основании** тело удалено: коммитмент команды хранителя либо хэш применённой политики. Удаление без названного основания неотличимо от потери данных — в этом смысл поля, а не в самом факте стирания.

**Внутренней подписи в записи нет намеренно.** Внешняя witness-запись уже подписана узлом, и `executor_node_id` называет исполнителя. Отдельная внутренняя подпись потребовала бы собственного подписанта и собственного доменного сепаратора, а при удалении по политике подписанта-человека не существует вовсе.

Отдельно названо: **сырое обоснование есть персональные данные хранителя-человека, а не данные существа.** Срок удержания, право на удаление и локализация — вопрос право-трека Ф0 по трём юрисдикциям (UA / KR / EE), и матрица выше даёт для него технический выход — удалить тело, сохранив доказательство того, что оценка была дана. Численные сроки в архитектурный документ не идут (§8).

До появления импортёра:

- запись не распространяется как canary;
- не входит в секретный резерв;
- не влияет на champion score, routing, reputation или slashing;
- не попадает автоматически в Smriti;
- не запускает training, fine-tuning, skill mutation или Profile adoption.

`UNKNOWN` никогда не является known-correct answer. `BAD` без `expected_outcome` также не может стать canary source.

### A10 · Persist-before-expose

Ответ считается готовым к показу хранителю только после:

1. terminal DecisionTrace;
2. Being signature над content commitment;
3. node witness commitment к тому же содержанию;
4. durable journal append;
5. успешной локальной проверки связности этих объектов.

Если persist или verification не завершены, UI показывает отказ/неопределённость и не выдаёт незафиксированный ответ как нормальный результат. Информационную экспозицию нельзя отменить после показа, поэтому exposure стоит после commit.

### A11 · Доказательный badge вычисляется, а не копируется из одного поля

G-GUI не отображает сырое `trace.state == VERIFIED` зелёным без проверки контекста. Badge выводится из:

```text
profile × trace.state × verifier_panel.mode × protocol_evidence_status
```

Минимальная таблица Ф0:

| Комбинация | Badge |
|---|---|
| production + независимая panel + `VERIFIED` | `VERIFIED` |
| dev + `mode=self` | `DEV · SELF-VERIFIED · NOT NETWORK-VERIFIED` |
| terminal refusal | `REFUSED` |
| неизвестная/противоречивая комбинация | `UNRESOLVED` |

Будущая строка Ф2:

| Комбинация | Badge |
|---|---|
| custody + `SELF_CHECKED` | `SELF_CHECKED · PENDING CORROBORATION` |

В Ф0 `SELF_CHECKED` остаётся зарезервированным и неэмитируемым. UI rendering проверяется вне WitnessChain на schema fixture, явно маркированной `synthetic`. Тест не создаёт ложного custody evidence.

### A12 · Agent Alpha не является ранней Chitta

Agent Alpha использует уже существующий BeingRuntime и тонкий seam для context/feedback. Он не включает:

- ChittaRuntime;
- Svādhyāya;
- Self-Model;
- Reflection Records;
- Improvement Hypotheses;
- skill mutation;
- automatic learning;
- Being Role Contest;
- Profile Gauntlet;
- network canary lifecycle;
- custody queue/temp memory runtime.

Feedback может стать входом этих будущих механизмов только через их собственные ADR и gates. Прямой путь `BAD → self-modification` запрещён.

### A13 · Containment: голос остаётся, рука останавливается

Agent Alpha сохраняет уже принятое правило:

- containment не запрещает recall, reasoning, pure response, чтение trace и guardian feedback;
- containment блокирует executive action в KriyaGate;
- GUI обязан явно показывать `CONTAINED` и не предлагать запрещённую команду как доступную;
- feedback о содержащемся Being не является командой release;
- G-GUI Ф0 не получает capability инициировать, снять или обойти containment.

### A14 · Профиль узла и профиль Being не смешиваются

`local_only` / `network_member` — профиль узла по ADR-019. `dev` / `production` — режим BeingRuntime текущей реализации. `Alpha Profile` — переносимая конфигурация продукта. Эти три оси независимы и не кодируются одним enum.

Существо на харнессе в Ф0 может работать на `local_only` узле. Переход узла к `network_member` не создаёт новое Being и не сбрасывает его history. Custody history, когда она появится, также не сбрасывается.

### A15 · Рождение на харнессе: новый ключ, пустая память

**Новое в rev 1.** Существа рождаются из подготовленного состояния харнесса — в этом смысл цифровой эволюции, и запрещать это не нужно. Запрет D3 здесь не задет: при рождении создаётся **новый keystore**, а значит новый `BeingID`, новый `BeingManifest` и **новая authored lineage, начинающаяся событием genesis в WitnessChain размещающего узла**. D3 запрещает два одновременно активных экземпляра **одной** `BeingIdentity`; здесь идентичностей две.

**Формулировка исправлена в rev 2, и ошибка стоит того, чтобы её назвать.** Rev 1 писала «собственная hash-chain с нулевой записи». Это неверно описывает архитектуру и проверяется по дереву: `WitnessChain` держит ключ **узла**, пишет `node_id` в тело каждой записи и подписывает ключом узла; строка `being_id` в `jjdai/witness.py` не встречается ни разу. Своей цепи у существа нет и не предполагалось. Собственная цепь у существа означала бы **параллельный свидетельский план** — прямое столкновение с INV-9, по которому свидетельство ведётся о существе, а не существом.

Правильно: цепь принадлежит узлу; существо имеет **authored lineage**, витнессируемую одним или последовательностью размещающих узлов. Непрерывность существа доказывается непрерывностью этой линии через смену хостов, а не наличием отдельной цепи.

Инвариант рождения:

> **Харнесс несёт конфигурацию и политику. Он никогда не несёт Smriti, witness-линию или keystore.**

**Память нового существа по умолчанию — ноль.** Smriti не копируется автоматически. Если создатель решит передать опыт, он загружает его **после рождения, отдельным актом** — с автором, временем и витнесс-записью.

Это не ограничение, а перенос вопроса туда, где ему место: наследование памяти перестаёт быть невидимым свойством рождения и становится действием, за которое кто-то расписался. Три следствия принимаются сразу:

* контаминация канареек **не наследуется по линии** — реестр портится только там, где загрузка действительно была;
* **родство не является отдельной осью независимости панели.** Два существа с одной core LLM коррелированы по provenance модели, и это уже покрыто correlation-constraint; отдельная ось линии не нужна;
* загруженная память есть опыт, который существо не прожило, и это порождает отдельный класс вопросов — атрибуция, различение прожитого и загруженного самим существом, полномочие того, кто загружает. Они **не помещаются в настоящий ADR** и выносятся в ADR-021 (§8).

### A16 · Версия харнесса подписывается, а не подразумевается

**Новое в rev 2.** A1 вводит `Alpha Profile(k)` как «версия харнесса × артефакт модели × backend × адаптеры × политики», но rev 1 не сказала, **чем доказывается версия харнесса**. Неподписанная версия в определении профиля означает, что evidence прогона ссылается на утверждение, а не на факт.

Решение: **отдельного `AlphaHarnessManifest` не вводится.** `harness_version` и `harness_hash` становятся **обязательными полями профильного манифеста**, попадающими в его канонизацию и подпись наравне с версиями backend, driver и runtime, которые он уже несёт.

**Миграция схемы, без которой это решение неисполнимо (rev 3).** Проверено по коду v0.6.8: `MANIFEST_SCHEMA_VERSION = "1"`, и валидация **отвергает неизвестные ключи** — намеренно, потому что иначе подпись перестаёт что-либо значить. Значит просто дописать два обязательных поля в существующую схему нельзя: уже подписанные манифесты станут невалидными, а новые не пройдут у старых читателей.

Вводится **`jjdai.model-artifact/v2`**:

| Правило | Значение |
|---|---|
| v2 | `harness_version` и `harness_hash` обязательны |
| Чтение v1 | сохраняется бессрочно — исторические манифесты подписаны и обязаны проверяться дальше |
| Запись v1 | прекращается с момента обязательности v2 |
| Момент обязательности | **первый прогон Alpha Host Conformance** (исправлено в rev 4) |
| v1 в decision path | не допускается после этого момента: манифест без версии харнесса не описывает поведение, которым принято решение |

**Точка перехода исправлена в rev 4.** Rev 3 назначала обязательность v2 на genesis `JaiGuruDev`, но conformance проходит **до** genesis, а гейт уже требовал `alpha_profile_manifest_evidence` с v2 на каждом прогоне: документ требовал v2 раньше, чем сам объявлял его обязательным. Правильно: **v2 обязателен с первого прогона Alpha Host Conformance, а genesis `JaiGuruDev` допускается только после успешного conformance на v2.** Порядок при этом сохраняет решение открытого вопроса 1 — существо создаётся после квалификации хоста, — и просто перестаёт ему противоречить.

Это ровно тот случай, ради которого схема с самого начала версионирована и отвергает неизвестные ключи. Правило то же, что для предгенезисного резерва: **поле, добавленное в подписываемую структуру, есть миграция, а не дополнение.**

Основание — экономия сущностей и уже принятая дисциплина: `ModelArtifactManifest` существует именно для того, чтобы связывать компоненты в один подписанный артефакт; отдельный манифест харнесса пришлось бы отдельно версионировать, отдельно подписывать и отдельно сверять, создавая второй путь расхождения. Имена полей предгенезисные и объявлены здесь.

Следствие, принимаемое сразу: **смена версии харнесса меняет профиль**, а значит по ADR-014 запускает новый Gauntlet в Ф3 — как и смена модели. Это правильно: харнесс несёт `ContextAssembler` и seam KriyaGate, то есть поведение, а не оформление.

## 3. Сериализуемые значения до genesis

До первой эмиссии в v0.6.10 резервируются имена **и фиксируются схемы**.

**Уточнено в rev 4.2 (P0-2 ревью r6.9).** Общее правило роадмэпа «в Ф0 замораживаются только имена, схемы — в Ф2» относится к трекам V и VI, которые в Ф0 ничего не эмитируют. К настоящему ADR оно **не применяется**: guardian-записи эмитируются в v0.6.10, то есть внутри Ф0. Для подписываемого, хэшируемого и append-only объекта заморозить имя, оставив тело на будущее, невозможно — подпись покрывает каноническое кодирование, и его изменение после первой эмиссии есть миграция, а не уточнение. **Схемы §3 фиксируются целиком до первой эмиссии, не в Ф2.**

### Виды записей

- `GUARDIAN_COMMAND`
- `GUARDIAN_FEEDBACK`

### Feedback enum

- `GOOD`
- `BAD`
- `UNKNOWN`

### Доменные сепараторы

- `JJDAI:GUARDIAN:COMMAND:v1`
- `JJDAI:GUARDIAN:FEEDBACK:v1`
- `JJDAI:GUARDIAN:BINDING:v1`
- `JJDAI:GUARDIAN:BINDING:REVOKE:v1`
- `JJDAI:GUARDIAN:FEEDBACK:BODY:v1`

Два последних **добавлены в rev 4**: rev 3 ввела подпись привязки и подпись отзыва с доменным разделением, но сами домены в резерв не попали. Домен, употреблённый в подписи и не объявленный до genesis, — предгенезисная строка, забытая на том же месте, где документ требует её объявить.

### Основание удаления тела

- `GUARDIAN_REQUEST`
- `RETENTION_POLICY`

### Область оценки

- `RESPONSE`
- `ACTION_OUTCOME`
- `WHOLE_TRACE`

### Поля, зарезервированные rev 4.2

- `subject_action_ids` — список идентификаторов действий трейса. **Не используется и не эмитируется в Ф0**: там действует ограничение «не более одного действия на размечаемый трейс» (§8.10). Резервируется сейчас, чтобы поштучная оценка в Ф2 была включением объявленного поля, а не миграцией схемы после genesis. Резерв стоит ноль; миграция после genesis невозможна;
- `policy_hash` — хэш артефакта политики удержания, обязательный в `FEEDBACK_BODY_ERASED` при основании `RETENTION_POLICY` (§8.5). Удаление, не называющее политики, отказывается.

`assessment_scope` **добавлен в rev 2**. Одна метка `GOOD`/`BAD` без него связывает качество ответа и исход действия одним кодом: «плохо» перестаёт различать неверный ответ и верный ответ, приведший к плохому исходу. Разделять после genesis — миграция.

### Класс доступа

- `GUARDIAN_PRIVATE`

### Виды записей — жизненный цикл привязки и удаления

- `GUARDIAN_BINDING_REPLACED` — **добавлен в rev 4.2**, см. A6-ter: замена привязки есть одно событие, а не пара «создать» и «отозвать»
- схема `jjdai.guardian-binding-replacement/v1` — **добавлена в rev 4.3.1**: подписываемая структура `ReplacementStatement`, над которой вычисляются обе подписи
- `GUARDIAN_BINDING_CREATED`
- `GUARDIAN_BINDING_REVOKED`
- `FEEDBACK_BODY_ERASED`

`GUARDIAN_BINDING_CREATED`, `GUARDIAN_BINDING_REVOKED` и `GUARDIAN_BINDING_REPLACED` несут trust root из A6-bis и A6-ter; `FEEDBACK_BODY_ERASED` — удаление приватного тела с сохранением коммитмента из A9. Схема `jjdai.guardian-binding-replacement/v1` видом записи не является: это каноническая структура, над которой вычисляются обе подписи замены. Формула «первые два… третий» описывала перечень до rev 4.3.1 и снята редакцией роадмэпа r6.9.5.

### Ключевой домен ADR-017

- `guardian_feedback`

Домен **добавлен в rev 1**. Draft 0 резервировал виды записей, enum, сепараторы и неймспейс, но ни одного ключевого домена — при том что A8 требует шифрованного хранения сырого обоснования. Без имени домена шифрование приехало бы в Ф2, а строку пришлось бы добавлять после genesis: тот же дефект, из-за которого ADR-017 и ADR-018 переводились в Accepted до сборки резерва v0.6.8.

### Локальный namespace

- `feedback/alpha/`

`feedback/alpha/` не является Plane H, Smriti, cognitive ledger, custody memory или canary store. Ordinary retrieval Being не получает к нему доступа.

**Два отдельных вида записей принимаются, свёртка в generic governance envelope отклонена** (открытый вопрос 2, решён). Свёртка помещает различие в type tag **внутри тела записи**, а v0.6.8 доказал, что тело безопасно ровно настолько, насколько его сканируют: там резерв отказывал имени как аргументу и принимал как значение. Молчаливое кодирование через свободный `detail` запрещено, а свёртка есть его мягкая форма. Имя, добавленное до genesis, стоит одну строку; после genesis это миграция реплицированного append-only стора.

Резерв обязан отказывать **на обеих осях** — и как аргумент, и как значение, — по правилу, выведенному из P0-1 v0.6.8 и записанному в сквозные принципы роадмэпа.

## 4. API / process boundary

G-GUI остаётся отдельным loopback-only процессом. Сетевое устройство:

```text
Browser/WebView
   ↕ loopback + origin/CSRF protection
G-GUI process
   ↕ mTLS + GuardianCommandEnvelope
Node daemon
   ↕ internal calls
BeingRuntime / Witness / Feedback Journal
```

Обязательные ограничения:

- G-GUI слушает только loopback;
- daemon admin/guardian surface не открывается наружу;
- browser origin фиксирован; CSRF token и strict CSP обязательны;
- command payload имеет size limit;
- counters и idempotency переживают restart;
- feedback endpoint не принимает trace другого Being;
- GUI не хранит raw key после lock/exit;
- неизвестная capability отказывается fail-closed;
- статический тест доказывает, что GUI call set является подмножеством `guardian_ui` allowlist.

## 5. Acceptance дропа Agent Alpha (v0.6.10)

### 5.1 Hermetic

1. Guardian key выводит стабильный `guardian_id`; переатрибуция отвергается.
2. Command signature, domain, target Being, counter и payload hash проверяются отдельно; каждый tamper-класс красный.
3. Replay command/feedback отвергается без второй записи.
4. G-GUI role не достигает ни одного operator-admin/test-hook endpoint.
5. `ContextAssembler` действительно передаёт recalled context модели; тест ломается, если оставить только citations в trace.
6. Context commitment открывается к точному ordered input; plaintext отсутствует в WitnessChain.
7. Feedback принимается только для terminal, correctly attested trace.
8. `GOOD/BAD/UNKNOWN` различимы; update append-only через supersedes.
9. Feedback не меняет trace, verification status, routing, reputation, Smriti или model/profile.
10. Alpha Feedback Journal и RAG/eval paths структурно не пересекаются.
11. Dev self-verification никогда не отображается как network `VERIFIED`.
12. Synthetic `SELF_CHECKED` rendering не эмитирует reserved token в chain.
13. Persist failure запрещает exposure и feedback acceptance.
14. Restart сохраняет `BeingID` **`JaiGuruDev`**, его authored lineage, trace, context commitments, guardian counters и feedback journal. У харнесса `BeingID` нет — формулировка исправлена в rev 2.

### 5.2 Live на основном хосте `JaiGuruDev`

**`JaiGuruDev` создаётся ПОСЛЕ успешного Alpha Host Conformance на его основном хосте** (открытый вопрос 1, решён). У существа одна непрерывная **authored lineage**, и оно не пересоздаётся: завести его до квалификации хоста значит оставить два плохих выхода, если хост не пройдёт, — гнать существо через migration consent по причине, которая не является настоящим фазовым переходом, либо бросить существо с реальной историей. Conformance для того и использует отдельные conformance-существа, что их падение ничего не стоит. Genesis существа не бывает репетицией.

Хранитель проводит минимум одну двухходовую сессию:

1. первый turn создаёт новое воспоминание;
2. второй turn требует использовать его;
3. host evidence доказывает, что recalled content вошёл в model input;
4. хранитель проверяет trace и provenance;
5. хранитель ставит один из трёх feedback codes;
6. feedback переживает restart;
7. тот же BeingID отвечает после restart.

### 5.3 Alpha Host Conformance

На **каждом из двух** целевых классов хоста прогоняется `tests/live/test_vertical_live.py` с настоящей моделью и отдельным conformance-существом. Вариант Alpha Profile выбирается по dense-размеру, который класс тянет. Evidence включает:

- host class;
- OS/runtime versions;
- backend and engine fingerprint;
- ModelArtifactManifest hash;
- checkpoint hash;
- node ID и test BeingID;
- acceptance result digest;
- версию Alpha Harness и идентификатор варианта Alpha Profile;
- подтверждение, что это **conformance-существо, а не `JaiGuruDev`**.

### 5.4 Gate result

Ф0 не закрывается количеством зелёных функций. Нужен evidence bundle:

```text
being_identity_evidence          # JaiGuruDev: ключ, BeingID, BeingManifest,
                                 # genesis-событие authored lineage в цепи узла
primary_live_session             # двухходовая сессия на основном хосте
guardian_authz_evidence
memory_grounding_evidence
feedback_journal_evidence
host_class_conformance[2]        # ДВА КЛАССА хоста: Linux x86-64, macOS Apple silicon
node_commissioning[3]            # ТРИ ФИЗИЧЕСКИХ УЗЛА testnet-0 — отдельный набор
guardian_binding_evidence        # A6-bis: привязка создана в церемонии genesis
alpha_profile_manifest_evidence  # A16: манифест v2 с подписанными harness_version
                                 # и harness_hash на каждом прогоне
negative_security_results
```

### 5.5 Отрицательные проверки — перечень, а не рубрика

Rev 2 сводила их к одной строке `negative_security_results`, и она ничего не обязывала. Перечень обязательных красных прогонов:

| # | Прогон | Ожидание |
|---|---|---|
| N-1 | подделанная `authority_signature` привязки | привязка отвергнута; ни одна команда по ней не проходит |
| N-2 | команда по **истёкшей** привязке (`not_after` в прошлом) | отказ |
| N-3 | команда по **отозванной** привязке | отказ, независимо от `issued_at` — двусторонняя проверка A6.8 |
| N-4 | команда по **заменённой** привязке (`previous_binding_hash` указывает на неё) | отказ; действует только текущая |
| N-5 | команда с `issued_at` **задним числом** сверх `COMMAND_MAX_AGE` | отказ |
| N-6 | команда с `issued_at` в будущем сверх clock skew | отказ |
| N-7 | повтор `command_id` / несогласованный счётчик | отказ |
| N-8 | оценка с `assessment_scope = ACTION_OUTCOME` **без** `subject_action_id` | отказ |
| N-9 | попытка узла прочитать приватное тело обратной связи | невозможно: ключ заворачивания у хранителя, узел держит только шифротекст |
| N-10 | попытка существа извлечь `GUARDIAN_PRIVATE` обычным путём или через `hypothesis_retrieval` | отказ |
| N-11 | `FEEDBACK_BODY_ERASED` | тело недоступно; коммитмент, метка, `assessment_scope` и witness-запись остаются валидными и проверяемыми |
| N-12 | манифест `jjdai.model-artifact/v1` в decision path **начиная с первого прогона Alpha Host Conformance** | отказ; чтение исторического v1 при этом продолжает работать |
| N-13 | вызов эндпоинта вне allowlist `guardian_ui` под валидным guardian-credential | отказ по политике, не по маршруту |
| N-14 | команда с `binding_hash`, указывающим на привязку **другого** target Being | отказ |
| N-15 | команда с валидной подписью хранителя, но чужим `credential_ref` | отказ |
| N-16 | команда, запрашивающая capability вне `capabilities` своей привязки | отказ |
| N-17 | команда с `binding_hash`, не разрешающимся ни в одну известную привязку | отказ |
| N-18 | запись обратной связи с **частичным** криптокомплектом (например, `ciphertext_hash` без `wrapped_dek`) | отказ по правилу «всё или ничего» A9-ter |
| **N-19** | `GUARDIAN_BINDING_REPLACED` без `revoke_signature` либо без `create_signature` | отказ. Половина составного события не является событием, и принятая половина — ровно то окно, ради закрытия которого A6-ter и введена |
| **N-20** | `previous_binding_hash` указывает не на действующую привязку (устаревшую, чужую, несуществующую) | отказ. Защита от гонки: два одновременных замещения, оба видевшие одно состояние, — второе обязано упасть, а не перезаписать первое |
| **N-21** | подписи проставлены ключом, не являющимся `authority_id` записи | отказ. Право заменять принадлежит названному авторитету, а не любому допустимому клиенту mTLS |
| **N-22** | две записи `GUARDIAN_BINDING_REPLACED` с одним `previous_binding_hash` | принимается ровно одна; вторая отвергается по N-20. Проверяется, что победила **первая по цепи**, а не последняя записанная |
| **N-23** | **крах узла между валидацией и записью**, затем рестарт | после рестарта существо имеет **ровно одну** действующую привязку — либо прежнюю, либо новую, никогда обе и никогда ни одной. Восстановление не «доигрывает» половину: незавершённой половины не существует |
| **N-24** | `new_binding` с телом, не соответствующим `new_binding_hash`; отдельно — `replacement_id`, не покрытый одной из двух подписей | отказ в обоих случаях. Второй — защита от вырезания половины составного события и предъявления её как самостоятельной записи |

## 6. Последствия

### Положительные

- появляется первый реально используемый Being, а не только trust-kernel;
- ручное тестирование начинается до XMR, Chitta и Plane B;
- уникальность Being не конфликтует с кросс-хостовой переносимостью Profile;
- human feedback получает provenance и не отравляет память/обучение автоматически;
- GUI не превращается в скрытый super-admin;
- evidence status остаётся честным в dev, production и будущем custody.

### Стоимость

- дроп Alpha требует ContextAssembler, guardian authn/authz и Feedback Journal, а не только frontend;
- понадобятся **шесть** новых предгенезисных record kinds (`GUARDIAN_COMMAND`, `GUARDIAN_FEEDBACK`, `GUARDIAN_BINDING_CREATED`, `GUARDIAN_BINDING_REVOKED`, `GUARDIAN_BINDING_REPLACED`, `FEEDBACK_BODY_ERASED`), новый ключевой домен, новый класс доступа и версия v2 схемы манифеста. **Шестой добавлен в rev 4.2** и в этом перечне до rev 4.3.1 отсутствовал — счёт, названный в прозе, разошёлся с §3 в том же круге, где §3 его и получил;
- у хранителя появляется вторая пара ключей — заворачивания, отдельно от подписной; keystore и RUNBOOK это отражают;
- rev 1 пересматривала A1 и потребовала дополнительного круга ревью; **rev 2 закрыла три P0 rev 1, rev 3 — пять P0 rev 2, rev 4 — три P0 rev 3**; концептуальных кругов больше не требуется;
- **ADR-017 получает узкую поправку A-1** (A9-bis) и подлежит правке отдельной строкой;
- объём дропа Alpha вырос на жизненный цикл `GuardianBinding`: это не UI-работа, а trust root, и без него guardian-путь недоказуем;
- удаление тела отзыва при сохранении коммитмента требует отдельного события и потому отдельного вида записи;
- Roadmap r6.8 требует ревизии A-ALPHA, G-GUI и критериев Ф0;
- production-рука существует раньше Alpha (T-TOOLSET в v0.6.9), но её класс эффекта — `pure`, и acceptance Alpha внешнего действия не доказывает.

## 7. Отклонённые варианты

### «Agent Alpha — просто название дропа»

Отклонено: не отвечает, чья идентичность продолжается и что именно нельзя клонировать.

### «Три хоста запускают один и тот же Being keystore»

Отклонено: создаёт concurrent selves и fork истории без принятого протокола.

### «GUI использует общий admin certificate»

Отклонено: blast radius интерфейса равен operator-admin, хотя функции Ф0 значительно уже.

### «GOOD/BAD сразу пишется в canary store»

Отклонено: label не содержит known-correct answer и обходит будущий Plane B admission.

### «Раз dev trace имеет state VERIFIED, показать VERIFIED»

Отклонено: смешивает self-verification и независимую verification, нарушая смысл ADR-019.

### «Считать список citation hashes memory-grounded dialogue»

Отклонено: модель не может использовать контекст, которого не получила.

### «Agent Alpha — одно конкретное Being» (позиция draft 0)

Отклонено в rev 1: описывает не ту вещь. Alpha есть эталонный харнесс, на котором рождаются разные существа с разными core LLM; правила непрерывности принадлежат существу, а не эталону.

### «Порядковый `BeingID` вида `j000000001`»

Рассмотрено и отклонено: требует глобального распределителя, общего порядка рождений в сети, которая по ADR-019 штатно работает при разделении (два изолированных узла выдадут один и тот же номер), и всё равно отдельной подписанной привязки к ключу. `BeingID` остаётся выведенным из ключа. Человекочитаемое обозначение возможно как отдельный слой Being Registry в Ф4.

### «Smriti копируется в новое существо при рождении»

Отклонено: делает наследование памяти невидимым свойством рождения. Загрузка опыта должна быть отдельным актом с автором, временем и витнесс-записью.

## 8. Открытые вопросы

**Семь вопросов draft 0 закрыты в rev 1:** A1-bis и §5.2 (1), §3 (2), A7 (3), A4 (4), A8 (5), A9 и §3 (6), A2 (7).

**Новые, к принятию rev 2 либо к отдельным ADR:**

1. **Атрибуция загруженной памяти.** Записи, переданные существу после рождения, несут атрибуцию источника — но, как установил ADR-021, **многие записи Smriti подписаны только размещающим узлом**, и подписи существа-автора в них может не быть вовсе. Держать их с чужой атрибуцией — значит, что часть Smriti есть цитирование чужого опыта; переподписать ключом получателя — заявление авторства над непрожитым, то есть ложное утверждение в хэш-сцепленном сторе. Первое верно, второе недопустимо; форма записи — предмет **ADR-021**.
2. **Различение прожитого и загруженного самим существом.** Если различает только сеть, существо построит Self-Model на опыте, которого у него не было, а `evidence_refs` трека V будут ссылаться на чужие свидетельства как на свои. Задевает bhoktritva. **ADR-021**.
3. **Полномочие загрузки.** «Создатель решит и загрузит» формирует то, что существо считает своим прошлым. Кандидат в отдельный класс blast radius рядом с П-7. **ADR-021**.
4. **Удержание персональных данных хранителя.** Сырое обоснование в `feedback/alpha/` есть персональные данные человека, а не данные существа. Срок удержания, право на удаление и локализация — вопрос право-трека Ф0 (UA / KR / EE), а не только криптографии. Удаление тела при сохранении коммитмента должно быть описано до первой эмиссии.
5. **Численные сроки удержания и юрисдикционные основания** для сырого обоснования хранителя (UA / KR / EE) — **право-трек остаётся открытым, но технический gate закрыт в rev 4.2.** Ревью верно указало, что `RETENTION_POLICY` как значение enum ничего не удерживает: автоматическое удаление обязано ссылаться на существующий, применимый и версионированный артефакт политики. Поэтому:
   * политика удержания есть **артефакт** `docs/retention_policy.json` с полями `policy_version`, `policy_hash`, применимостью по юрисдикции и сроком по классу данных;
   * запись `FEEDBACK_BODY_ERASED` с основанием `RETENTION_POLICY` **обязана нести `policy_hash`** той политики, по которой удаление произошло. Удаление, не называющее политики, отказывается;
   * **gate (исправлен в rev 4.3):** первая запись персональных данных хранителя (`feedback/alpha/`) не производится, пока в дереве нет действующей политики, применимой к юрисдикции хоста.

     Формулировка rev 4.2 «нет политики — нет тела, только commitment» **противоречила A9-ter** и здесь снимается. По правилу «всё или ничего» приватного тела не бывает наполовину: `body_commitment` есть одно из **пяти** полей комплекта, а не остаток, переживающий его отсутствие. Запись с одним `body_commitment` и без `ciphertext_hash`, `object_dek_id`, `wrapped_dek` и `wrapping_metadata` — частичный комплект, который A9-ter отвергает.

     Действующая норма: **без действующей политики сохраняется только публичная подписанная запись обратной связи** — оценка, область оценки, привязка, коммитмент трейса, — а **все пять полей приватного тела отсутствуют**. Хранитель при этом видит в интерфейсе, что сырое обоснование не сохраняется, и почему;

     `FEEDBACK_BODY_ERASED` к этому случаю **не применяется**: удалять нечего. Запись об удалении тела, которого никогда не было, утверждала бы, что оно существовало.

   Численные сроки остаются вопросом право-трека. Механизм удаления **решён полностью** в A9-ter: `FEEDBACK_BODY_ERASED` с двумя основаниями, `basis_commitment` и исполнителем; тело удаляется, коммитмент, метка, `assessment_scope` и witness-запись остаются. Открыты только сроки и то, какие юридические события считаются основанием класса `RETENTION_POLICY`.
6. **Платформенная независимость кросс-чека Ф2** при двух классах хоста без ускорителя (см. A4).
7. **Конкретные ступени dense-размеров** Alpha Profile — факт снабжения, а не архитектуры; уходят в план реализации v0.6.10 и в Execution Annex.
8. **Разделение полномочия оператора над `GuardianBinding`.** В Ф0 оператор может подменить того, кто говорит за хранителя; защита — витнессированность и append-only история, то есть обнаружимость, а не невозможность. Предмет ADR о succession, owed к Ф4.
9. **`COMMAND_MAX_AGE` и допустимый clock skew** для guardian-команд (A6) — **ЗАКРЫТ для Ф0 в rev 4.2; калибровка остаётся задачей Ф2.** A6 уже устанавливает `COMMAND_MAX_AGE = 300 с` и допустимый skew `±60 с`; §8 продолжал числить это открытым, то есть один раздел принимал решение, а другой считал его непринятым. Значения Ф0 действуют; пересмотр по данным эксплуатации — Ф2.

   Прежняя формулировка вопроса, сохранённая как основание: Слишком короткий срок ломает работу при расхождении часов на хосте; слишком длинный расширяет окно предъявления задним числом. Объявляется в Ф0, калибруется в Ф2.
10. **Гранулярность `assessment_scope` — ЗАКРЫТ в rev 4.2.** Вопрос сам требовал закрытия до первой эмиссии, а эмиссия теперь назначена в v0.6.10, поэтому оставлять его открытым больше нельзя. Решение из двух частей:
   * **в Ф0 трейс, размечаемый областью `ACTION_OUTCOME`, несёт не более одного действия.** Разметка трейса с несколькими действиями отказывается закрыто с кодом причины, а не размечается приблизительно. Однозначность покупается ограничением, а не толкованием;
   * **поле `subject_action_ids` (список) резервируется сейчас**, до genesis, вместе с остальными строками §3. Оно не используется в Ф0 и не эмитируется, но существует — поэтому расширение до поштучной оценки в Ф2 будет включением зарезервированного поля, а не миграцией схемы. Резерв стоит ноль; миграция после genesis невозможна.

## 9. Требуемые правки Roadmap после принятия

1. A-ALPHA: ввести четыре термина A1 дословно — **Alpha Harness** (клонируется), **Alpha Profile(k)**, **существо на харнессе** (не клонируется), **Alpha Host Conformance** — и назвать `JaiGuruDev`. Формулировка rev 1 «заменить „узел" на конкретное Being» была унаследована из draft 0 и противоречила собственной A1. *(Пункт 10 rev 2 дублировал этот и удалён.)*

3. G-GUI: `admin` заменить на `guardian_ui`; operator-admin оставить отдельным.
4. G-GUI: «новых endpoints нет» заменить на «новых capability нет».
5. G-GUI: «два фактора» заменить на password + optional biometric presence.
6. Дроп Alpha (v0.6.10): добавить ContextAssembler и signed feedback objects.
7. Acceptance дропа Alpha (v0.6.10): добавить dev-self evidence badge и persist-before-expose.
8. Ф0 gate: развести три набора evidence — живую сессию `JaiGuruDev`, **два** прогона `host_class_conformance`, и **три** `node_commissioning` физических узлов testnet-0. Два класса хоста не отменяют ввода в эксплуатацию трёх машин; это разные счётчики.

10. A-ALPHA: записать рождение с нулевой Smriti и загрузку памяти как отдельный витнессированный акт.
11. Ф1 gate: усилить требование к оффлайновым бэкапам keystore — degraded-профиль покрывает большинство узлов.
12. Ф2: записать ограничение платформенной независимости кросс-чека либо появление машины с ускорителем.
13. Дроп Alpha (v0.6.10): добавить жизненный цикл `GuardianBinding` (A6-bis и A6-ter) в объём дропа — без trust root guardian-путь не доказуем.
14. G-GUI Ф0: убрать изменение постоянной guardian policy из перечня возможностей интерфейса.
15. A-ALPHA: `harness_version` и `harness_hash` — обязательные подписанные поля профильного манифеста (A16).
17. **Ф0 gate (rev 4.2):** развести основной сеанс и работу интерфейса на трёх узлах. Полная сессия `JaiGuruDev` — **одна, на основном хосте**; conformance-прогоны идут отдельными существами на двух классах хоста; ввод в эксплуатацию — три машины. Требование «хранитель на каждом из трёх узлов провёл диалог и разметил исход» относится к **гейту Ф1**, где оно уже есть, и в Ф0 только расширяет критический путь Alpha, смешивая три независимых набора evidence обратно в один.
18. **Ф0 gate (rev 4.2):** дроп Alpha не закрывается без полного прохождения §5.1–5.5 настоящего ADR, включая отрицательные проверки N-1…N-24 и **persist-before-expose**. Роадмэп требует показать трейс и provenance, но не фиксирует последовательность `terminal trace → подпись Being → commitment узла → устойчивая запись → проверка связности → и только затем показ ответа`; без неё gate формально закрывается ответом, показанным до фиксации.
19. **Объём дропа Alpha (rev 4.2):** внести приватную часть обратной связи — отдельную пару `guardian_wrap`, клиентское шифрование в G-GUI, объектный DEK, правило «пять полей — всё или ничего» (A9-ter), недоступность тела узлу и существу, `FEEDBACK_BODY_ERASED` и сохранение коммитмента после удаления. Формулировка «подписанные объекты обратной связи» теряет половину принятого формата `GuardianFeedbackRecord`.
20. **Ф0 gate (rev 4.2):** внести отдельный keystore хранителя с двумя парами ключей и его backup/export с degraded-статусом, названным **и в RUNBOOK, и в интерфейсе** (A7). Усиление бэкапов keystore **узлов** этого не покрывает — это другой keystore.
21. **G-GUI Ф0 (rev 4.2):** `SELF_CHECKED` в Ф0 **не эмитируется** — custody runtime стоит в Ф2. Проверяется только рендеринг бейджа на синтетической фикстуре, которая в WitnessChain не попадает; настоящий custody-бейдж включается в Ф2.
22. **Правила заморозки (rev 4.2):** правило «в Ф0 замораживаются только имена, схемы — в Ф2» относится к трекам V и VI, которые в Ф0 ничего не эмитируют. Схемы ADR-022 фиксируются целиком до первой эмиссии в v0.6.9, схемы настоящего ADR — до первой эмиссии в v0.6.10.
16. **Ф0 / трек I: миграция `jjdai.model-artifact/v2`** — правила чтения v1 и v2, обязательность v2 **с первого прогона Alpha Host Conformance**, запрет v1 в decision path с того же момента, genesis `JaiGuruDev` только после успешного conformance на v2. Затрагивает трек I, а не только A-ALPHA.
